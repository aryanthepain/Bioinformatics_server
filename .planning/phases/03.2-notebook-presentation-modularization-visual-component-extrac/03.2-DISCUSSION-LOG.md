## Discussion Record

### Area 1: Module Architecture & Import Strategy
- **Question**: Where should the extracted functions live and how should they be exposed?
- **Decision**: Keep strictly in `quaternary/presentation.py` without polluting the high-level `quaternary_pipeline` facade.
- **Question**: Should the render_* functions return the HTML object in addition to displaying it?
- **Decision**: The functions construct and return the `IPython.display.HTML` object directly. The function itself does *not* invoke `display()`. This enables pure functional rendering, testability without mocks, and caller-controlled presentation.

### Area 2: Notebook Presentation Layout
- **Question**: In the presentation notebook cells, how should the visualizers be invoked?
- **Decision**: Explicit `display()` calls (e.g. `display(render_quaternary_summary_card(output))`) across all visualizer cells.
- **Question**: Where should the presentation imports live in `Quaternary_Structure.ipynb`?
- **Decision**: Single consolidated presentation imports cell (Cell 2) importing all `render_*` and validation helpers at the top of the notebook.

### Area 3: Test Coverage & Edge Cases
- **Question**: How should the tests for presentation functions be structured?
- **Decision**: Author `tests/test_presentation.py` with granular unit tests per function (covering valid inputs, edge cases, fallbacks, and HTML assertions), AND realign existing notebook tests to verify clean imports.
- **Question**: What edge case scope should be tested for the presentation functions?
- **Decision**: Test both normal rich data AND edge case fallbacks (empty interfaces, uncharacterized proteins without homologs, invalid/empty accession strings).
